# v0.10.0: Severity of review findings and re-review against the previous round (interface 1.5)

[简体中文](../../releases/v0.10.0.md) | English

This is the minor release after v0.9.0, for the "automatic takeover" flow: Codex review findings are split into blocking and suggestion, blocking findings are fixed and re-reviewed, and anything still unresolved after two rounds goes to a person. **From this release every review finding carries `severity`, and a re-review can take the previous round's report to check, item by item, whether its blocking findings are resolved.** The interface description moves from `1.4` to `1.5` and only adds fields; the report `schema_version` stays `1`. Without the new option nothing changes and no migration is needed, but report readers should know that `findings` gains a field (see below).

This comes from the ecosystem ledger S101 "automatic takeover" merged plan, which the user approved on 11-21 in the user's words 「按推荐批准」 — "approved as recommended". The delegate part was split into two modules, review-severity and review-recheck, whose specifications, plans and delivery acceptance were each approved by the user in this session; the usage draft is [spec/usage/auto-takeover-review.md](../../../spec/usage/auto-takeover-review.md).

## Changes

### Severity of review findings

- Each finding gains the required field `severity`: `blocking` or `suggestion`. The review model labels it against the fixed criteria `severity-v1`, drafted by autopr-design and approved by the user; the full text is in the [review-severity spec](../SPEC-review-severity.md). `--task` cannot change the criteria, and any later change takes a new name.
- A finding that would be blocking if true but cannot be confirmed is labelled `blocking`, with what could not be confirmed listed in `unverified`.
- If the model omits the value or gives a wrong one, the whole review is `failed` (diagnostic `finding_invalid`); delegate does not fill it in.
- Report readers: treat a missing `severity` (reports from v0.9.0 and earlier) or an unknown value as `blocking`; read it only when `execution_status=completed` and the review has a conclusion; no blocking findings does not mean the change may be merged.

### Re-review against the previous round

- `/delegate:review` gains `--previous-report <previous report>`. The previous round's blocking findings (and, when the previous round was itself a re-review, its still-unresolved old items) go item by item into the new report field `recheck.items`, marked `resolved` or `unresolved` with evidence; this round's `findings` holds only new issues. The contract is in the [review-recheck spec](../SPEC-review-recheck.md).
- The previous report must come from delegate, have a conclusion and the same scope (for `commits`, the same `--base`; `--head` may move forward). Otherwise `previous_report_unreadable`, `previous_report_invalid` or `previous_report_scope_mismatch`, exit 127, no model started. An incomplete per-item answer from the model gives `recheck_invalid` and a `failed` review.
- This round's blocking set = `unresolved` entries in `recheck.items` + `findings` treated as `blocking`. Round counting and hand-off to a person are the caller's decision. To check that the re-review covered the fixed patch, compare `recheck.previous_fingerprint` with this round's `scope.fingerprint`.
- Without the option, `recheck` is `null`.

### Interface 1.5

In `interface.json`, `review.report` gains `severity` (field, values, criteria name `severity-v1`, missing treated as `blocking`), and `review` gains `recheck` (option `--previous-report`, field `recheck`, statuses `resolved`/`unresolved`).

## Validation and known limitations

Every behavior got a test that was confirmed to fail before the implementation (exceptions are listed in the module todos). A new `test-review-recheck.py` plus cases in the result, execution, context, cli and interface suites; review-severity added `severity` to 5 existing test fixtures to follow the contract, without changing any assertion. Free validation covers 388 Python, 53 shell and 19 eval checks, with 28 loop-registered Python regression suites; `claude plugin validate` passes for both the marketplace and the plugin.

**None of the following has been tested live:** whether both backends accept the new output structure at run time (the `severity` enum, and `previous` on a re-review); how accurately the model labels against the criteria and judges "resolved"; the guest path (needs a disposable VM). Per the usage draft, after release U1 and U2 are run against the installed version (calls Codex, paid) for the user to judge. The other unverified items listed in v0.8.0 are unchanged.
