# v0.6.0: Resumable delegation, fixed no-approval Codex calls

[简体中文](../../releases/v0.6.0.md) | English

A minor release after v0.5.3. It adds resumable delegation and moves the interface description to `1.1`. Every call that has Codex carry out work now uses a fixed approval mode, which changes behavior in write mode; see "Behavior changes" below. Without the new options, command usage and the report format are unchanged.

## Added

- **Resumable delegation ([run-resume](../SPEC-run-resume.md))**: `/delegate:run --resumable` lets Codex do the parts that do not depend on a pending decision, then stop and return `needs-input` when the user has to decide something; `/delegate:run --resume <runId> -- "<answer>"` continues the original Codex session with the user's answer. Off by default. Every successful return ends with the run_id and end status (`done` or `needs-input`).
- **Interface description `1.1`**: `interface.json` only adds `run.resume` (`optIn: "--resumable"`, `option: "--resume"`, backend `codex`, statuses `done` / `needs-input`); `review.command`, `doctor.command` and the other fields are unchanged. Consumers check `>=1.1,<2.0` to decide whether resume is available; when they read `1.0` or the field is missing, they keep the previous behavior and do not resume.

## Behavior changes

- **Every run and Codex review passes `approval_policy="never"`**: plain runs (read-only and write), resumable runs, resumes and the Codex review backend all pass `-c approval_policy="never"` instead of the approval mode in the local Codex configuration. Probe-only commands that use no model (`codex --version`, `codex login status`, `codex features list`) are unaffected.
- **Out-of-sandbox commands in write mode are refused**: previously, with a local approval mode such as `on-request`, an out-of-sandbox command could be approved and run; now no approval is requested and the command is refused. Write tasks that need to leave the sandbox (for example commands that rely on extra allow rules) may fail as a result.
- This change removes the risk of out-of-sandbox requests on read-only paths being approved on the user's behalf. During development, a resumed read-only resumable run wrote a file under the local `approval_policy="on-request"` with `approvals_reviewer="guardian_subagent"`; with `never`, the same task no longer wrote it.
- About v0.5.3 and earlier: read-only runs start in a read-only sandbox but do not fix the approval mode. When the local configuration uses an approval mode that can approve on the user's behalf (such as `on-request` with `guardian_subagent`), out-of-sandbox requests can technically be allowed, and whether anything is written depends mainly on the "do not modify files" instruction in the prompt. In a check with the v0.5.3 read-only run no file was written, because the model followed the prompt and did not try to write. The v0.5.3 Codex review ignores the user configuration and has no command-execution tool, so it is not affected. If you use read-only runs with such a configuration, upgrading is recommended.

## Validation and known limits

Free aggregate validation covers 196 Python cases (23 more than v0.5.3, 20 of them for resume), 53 shell and 19 eval, with 17 loop-registered Python regression suites; `claude plugin validate` passes for both the marketplace and the plugin.

Paid real checks (Codex CLI 0.162.1; records in the [run-resume task log, in Chinese](../../../tasks/run-resume/todo.md)):
- A read-only resumable run first returned `needs-input`; after resuming, the context carried over and it returned `done` without writing a file.
- A plain read-only run from current source did not write a file with the same prompt.

Not yet verified:
- The sandbox's technical blocking of write commands under `approval_policy="never"` was not directly exercised: in the checks above the model did not try to write, and no write command was refused by the operating system.
- Real write-mode run behavior under `never` (for example `git commit` relying on prefix allow rules) was not tested.
- The Codex review event stream under the local configuration was not saved and cannot be checked step by step.

The other unverified items listed for v0.5.0 are unchanged.

## Updating

Run `claude plugin update delegate@delegate-marketplace`, then open a new session or run `/reload-plugins`. Upgrading from v0.5.3 needs no migration; if your workflows use write-mode runs, note the behavior changes above.
