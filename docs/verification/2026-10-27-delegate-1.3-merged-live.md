## 计划调整（照实记录）

原计划第 2 步是在第 1 步（只读）的链上 `--continue --write`。按 run-continue 规格，`--write` 必须与原运行一致，所以这一步必然被拒（计划设计错误）。实测中做了两件事：先免费验证这一拒绝；再用写模式新起一条链，在它上面做 `--continue --write --authorized-by --check`。因此多用 1 次调用，总数仍在批准的上限内。

## 第 1 步：`--resumable --strict --rules-file`（调用 1）—— 成立

`run --resumable --strict --rules-file rules.md -- '读取 data.txt，告诉我第一行里的 token。'`

- 退出 0。答复首行是 `DONE: 第一行的 token 是 \`d6037aee\`，\`data.txt\` 总共 3 行。`：
  - **AGENTS.md 要求首行写「【报告】」，`--strict` 的结束标记段压过了它**；
  - 规则片段被照做（答复里写了总行数）。
- stdout 末尾三行依次为：用量行、`delegate: result=<路径>`、结果行 `status=done resumable=true`，结果行仍在最后。
- 结果文件与 `.events.jsonl` 逐项一致：
  - `sessionId` 等于 `thread.started.thread_id`；
  - `commands` 一条（`awk … data.txt`，退出 0），与事件中的 `command_execution` 相同；
  - `usage.session.inputTokens` 50,236，等于事件里 `turn.completed`；链首轮的 `usage.run` 与 `usage.session` 相同。
- 结果文件的其余字段：`markers.done` 为标记后的原文；`kind: run`，`chainRoot` 是自身；`timeoutSeconds: 540`；`authorization: null`（只读）；`rules` 只有路径、sha256、字节数，结果文件里搜不到规则原文。状态文件含 `strict: true`、`usageTotal`。

## 第 2 步：`--continue --write --authorized-by --check`

**2a（免费，未调用 Codex）：** `run --continue <第 1 步> --write --authorized-by grant.txt …` → 退出 64，`delegate: write mode mismatch`。

**2b（调用 2）：** `run --resumable --write --authorized-by grant.txt -- '只读一下 data.txt 的行数并回答，这一轮不要改任何文件。'`。退出 0；元数据有一行「写入授权：文件 …/grant.txt（sha256 63304e414a47）」，结果文件 `authorization` 为 `{source: file, path, sha256, bytes: 52}`。这一轮没带 `--strict`，答复首行是「【报告】」（AGENTS.md 生效），正好和第 1 步对照。

**2c（调用 3）：** `run --continue <2b> --write --authorized-by grant.txt --check './check.sh' -- '创建文件 b.txt，内容只有一行 ok。不要改别的文件，不要提交。'`。

- 退出 0，`b.txt` 恰为一行 `ok`，没有提交。
- stdout 中「检查：通过」「写入授权：…」两行都在 Git 验收块之前；Git 验收块列出 `?? b.txt`。
- 结果文件：
  - `kind: continue`，`parent` 指向 2b，`chainRoot` 是 2b；会话 ID 与 2b 相同，说明是在同一会话里接着做的。
  - `changedFiles` 为 `["?? b.txt"]`。
  - `check` 为 `{status: passed, exitCode: 0, argv: ["./check.sh"], tail: "b.txt ok"}`：检查命令在真实工作区执行。
  - **`usage.run.inputTokens` 63,224 = 本轮 `usage.session` 108,218 − 2b 的 44,994**，差值正确。
  - `commands` 两条，与事件一致。

## 第 3 步：`--resumable --timeout 660`，宿主后台模式（调用 4）—— 部分成立

`run --resumable --timeout 660 -- '按顺序做 8 步，第 N 步单独运行 sleep 55 && echo step-N …'`，在 Claude Code 的后台任务里运行，等完成通知，没有轮询。

- 退出 0，8 行输出全对；结果文件 `status: done`、`timeoutSeconds: 660`、`wrapUp: null`、`cleanup: null`，记录了 10 条命令，退出码都是 0。结束后没有残留的 `sleep 55`。
- **没有形成「超过 540 秒仍正常结束」的场景**：总耗时 500 秒（结果文件 `durationSeconds: 499.0`），每步约 62 秒。按批准时的约定不重试、不加跑。超过 540 秒的真实运行能正常结束、答复文件写对，有 S38 前置实测 T5a 的旁证（656 秒，经 `run_codex.py 700`），但那次没有经过 `--timeout` 这条路径。
- `--timeout` 的期限换算（`M = 615`）与传给 `run_codex.py` 的参数，由 run-longrun 的桩测试覆盖；本次实测只确认了带 `--timeout 660` 的真实运行能正常完成、结果字段正确。
