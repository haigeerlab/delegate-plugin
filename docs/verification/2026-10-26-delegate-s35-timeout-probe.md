# S35 前置实测：中止后续跑与到期前收尾

2026-10-26。起因是生态方案 S35（超时保留进度、超时可续跑），ecosystem-lead 受理原话：「S35 受理：先实测两个没验证的假设（中止后还能不能 resume、到期前能不能提示收尾），结果报你，再写 Spec 给我审；接口 1.2 只增不改。」本记录只做实测，不写 Spec、不改产品代码。

- 基准：main `64b5fd7`（v0.6.0）。Codex CLI `0.162.1`；日志头显示模型 `gpt-6.1-sol`、推理档 `none`（本机默认，未指定 `-m`/`--effort`）。
- 授权：用户在本会话原话「授权按计划实测，8 次，最多 10 次付费调用。」实际用了 **8 次**。补测（见文末）另行授权：用户看过补测计划（5 次、最多 7 次）后原话「继续」，实际用了 **6 次**。
- 临时仓库：`~/delegate-s35-probe-20261026192637`（10 个 `stepNN.txt`，每个存一个随机口令；模型不读文件就答不出）。测后 `git status` 为空，经用户同意已删除。
- `~/.codex/config.toml` 首轮 8 次测前测后 sha256 都是 `c84d6a4b…3c8b`，没改。补测中写模式运行让 Codex 自己追加了一条信任记录，见文末「补测」。本机配置仍是 `approval_policy = "on-request"` + `approvals_reviewer = "guardian_subagent"`；每次调用都和产品一样固定传 `-c approval_policy="never"`，日志头均为 `approval: never`、`sandbox: read-only`。

## 怎么测

驱动脚本原文见 [2026-10-26-delegate-s35-timeout-probe.py.txt](2026-10-26-delegate-s35-timeout-probe.py.txt)。它按 `codex-exec.sh` 的参数直接调 `codex exec`：

```text
env -u OPENAI_API_KEY -u CODEX_API_KEY DELEGATE_REVIEW_DEPTH=1 codex exec \
  -c forced_login_method="chatgpt" -c model_provider="openai" -c approval_policy="never" \
  --sandbox read-only --color never -o <answer> -- <prompt>        # stdin=/dev/null，不带 --ephemeral
codex exec resume <同上 -c 三项> -c sandbox_mode="read-only" -o <answer> -- <会话ID> <prompt>
```

任务（前面接 delegate 只读 run 的「非交互委托」开头）：按顺序做 10 步，第 N 步单独运行 `sleep 8 && cat stepNN.txt` 并记下口令，最后列出 10 个口令。不中止约需 2 分钟。为了省钱，把 540 秒按比例缩到 45 秒（中止时一般做完 3 步、第 4 步在跑）。

中止方式三种：纯 SIGTERM（最多等 15 秒）、纯 SIGKILL、直接经产品 `run_codex.py <45>`（SIGTERM → 2 秒 → SIGKILL，退出 124）。

## 假设 1：中止后能不能续跑 —— **成立**

| 编号 | 中止方式 | Codex 退出 | 中止时进度 | 续跑输入 | 续跑结果 | 续跑耗时 |
|---|---|---|---|---|---|---|
| E1a / R1a | 45 秒 SIGTERM | 18 ms 内退出，**退出码 0**，`-o` 答复文件**没写** | 1–3 步完成，第 4 步命令在跑 | 「已完成的不要重做，从下一步接着做完」 | 首行「接续自第 4 步」；日志里只执行了 step04–step10，1–3 没重做；10 个口令全对 | 81.1 s |
| E1b / R1b | 45 秒 SIGKILL | 退出 -9，答复文件没写 | 同上 | 「不要再执行命令，只写进度」 | 列出 1–3 步口令（全对），说明第 4 步已发起但被中止、下一步从第 4 步开始；**执行命令 0 条** | 12.6 s |
| E1c / R1c | `run_codex.py` 45 秒超时 | 124，答复文件没写 | 同上 | 同 R1b | 同 R1b，口令全对，执行命令 0 条 | 10.7 s |

细节：

- **会话 ID 怎么拿到**：过程日志第 11 行就是 `session id: <uuid>`，在模型开始工作前就写出，所以中止时一定已经在日志里（三次都是）。`run_state.py` 现有的 `session_id_from_log` 能直接取到。续跑日志头的 session id 与原会话相同。
- **会话文件**：`~/.codex/sessions/YYYY/MM/DD/rollout-…-<uuid>.jsonl` 在跑的过程中逐条写入。SIGTERM 与 SIGKILL 后都是 29 行、每行都是合法 JSON、以换行结尾。已完成步骤的「工具调用 + 结果」成对在里面；最后一条是第 4 步的工具调用（`custom_tool_call`），**没有对应结果**，也没有任何「中止」标记。
- **半截工具调用**：续跑时 Codex 没有报错，也没有往会话文件里补一条结果，模型自己判断出「第 4 步已发起但被中止」，并把它当作未完成的步骤重做（R1a）。
- **记忆**：随机口令 1–3 在续跑中没有重新读文件就答对，说明是从会话上下文里来的，不是猜的。
- 只看到 SIGTERM 下 Codex 退出码为 0、不写答复：经 `run_codex.py` 时外层按超时返回 124，不受影响；但不能用「Codex 退出 0」判断它正常做完。

## 假设 2：到期前能不能提示收尾 —— **两种做法在本测试里都成立，各有前提**

### 做法 (a)：先中止，再续跑一轮只要进度

即上表 R1b、R1c：续跑提示词只要求「不要再执行任何命令，只写进度」，两次都**零命令**、**10.7–12.6 秒**拿到准确的进度说明（已完成步骤 + 结果、做到一半的步骤、下一步从哪开始）。按这个量级，540 秒期限里主运行留出几十秒余量、再跑一轮收尾，在时间上是装得下的；但补测 V2 出现过一次 185 秒的服务端长尾，见文末。

前提与风险：

- 收尾轮本身也是一次 Codex 调用，也要有期限；它的耗时跟会话上下文大小有关，本测试上下文很小，真实大任务上的耗时**未验证**。
- 收尾轮要求续跑，所以主运行**不能带 `--ephemeral`**。今天的普通 run 都带 `--ephemeral`，中止后没有会话文件可续；S35 若要覆盖普通 run，必须改这一点。
- 中止发生在一条命令执行到一半时，那条命令的输出丢失，进度说明只能说「做到一半」，不能给出它的结果。

### 做法 (b)：提示词里约定时间预算

提示词写明开始时间（epoch 秒）、总预算 60 秒、到点会被强制中止且不保留答复；每步命令前先 `date +%s`；某步开始前已用时 ≥ 45 秒就不再开始新步骤，立即写最终答复。兜底在 90 秒 SIGKILL。

| 编号 | 正常退出时间 | 完成步骤 | 答复 |
|---|---|---|---|
| E2b1 | 58.9 s（退出 0） | 1–4 | 「已达到 45 秒停止阈值」，列出 1–4 口令（全对）、05–10 未完成、下一步从 05 开始 |
| E2b2 | 56.9 s（退出 0） | 1–4 | 同上，并写明第 4 步开始时间与「执行 8 秒后累计已超过 45 秒」 |

两次都在 60 秒预算内自己收尾，没有触发兜底，没有执行第 5 步（日志里只有 4 条命令）。但余量只有 **1.1–3.1 秒**：

- 模型自己没有时钟，只能从命令输出里的 `date` 推算；它是在第 4 步结束后推算「已超过 45 秒」才停的，从最后一次时间读数（约 +40 s）到退出又过了 17–19 秒。
- 本测试每步固定 8 秒，模型能事先估计；如果某一条命令本身要几分钟（例如全量测试），模型在命令跑完前没有机会检查时间，预算约定挡不住。
- 启动开销约 8 秒（第一条命令的时间读数比开始时间晚 8 秒），也要算进预算。

### 比较

- (a) 不依赖模型自觉守时，能在任意时刻中止；代价是多一次调用、主运行不能 `--ephemeral`、正在执行的那条命令结果丢失。
- (b) 不多花调用，答复直接出现在主运行的 `-o` 文件里；但依赖模型守约，碰到长命令会失效，阈值与期限之间必须留出「最长单条命令 + 收尾」的余量。
- 两者可以叠加：(b) 作为第一道，(a) 作为超时后的补救。是否这样设计留给 Spec。

## 顺带发现：killpg EPERM 竞态在本机可复现

驱动脚本在进程组退出后再 `os.killpg(pid, SIGKILL)`，空跑时（假 codex）出现过一次 `PermissionError: [Errno 1] Operation not permitted`，真实 E1b（SIGKILL 后再清理进程组）又出现一次。`run_codex.py` 的 `stop_group` 只捕获 `ProcessLookupError`，同样的竞态会让它抛出未捕获异常。本记录只证实现象可复现，修复不在本轮。

## 补测（同日，6 次付费调用）

用户问「还没验证的是否先验证下」，按会影响 Spec 的三项补测。临时仓库 `~/delegate-s35-probe2-20261026195358`：6 个约 64KB 的 `bigNN.txt`（各藏一行 `PASSWORD-N`）与 10 个 `stepNN.txt`。驱动脚本加了 `PROBE_SANDBOX`、`PROBE_EFFORT`，分别对应 delegate 的 `--write` 与 `--effort`（续跑时沿用同一推理档，与 `codex-exec.sh` 一致）；配套原文已更新为这一版。

### V1 写模式中止后续跑 —— 成立（有前提）

- 任务：6 步，第 N 步 `sleep 8 && echo "line-N" >> out.txt`，`--sandbox workspace-write`，经 `run_codex.py` 30 秒超时（退出 124）。中止时 `out.txt` 有 `line-1`、`line-2`。
- 续跑（`-c sandbox_mode="workspace-write"`）：「已完成的不要重做……开始前可以先查看 out.txt 确认做到哪一步」。Codex 先 `cat out.txt`，从第 3 步接着做到第 6 步；最终 `out.txt` 恰好 `line-1`…`line-6`，没有重复行、没有缺行。首行「接续自第 3 步」。59.0 秒。
- 前提：提示词里提示了「先看文件确认进度」；不提示时会不会重复追加没测。中止落在 `sleep` 期间，没有出现「写到一半的文件」；真正半截写入的情况没测。

### V2 大上下文 + high 推理档时收尾轮耗时 —— **不稳定，出现 185 秒长尾**

- 起跑：`high` 推理档，6 步各 `cat bigNN.txt` 读完整文件。计划 90 秒中止，但它 75.9 秒就做完了，**没有形成中止场景**。会话上下文约 3.4 万 token（单轮输入 34k，其中缓存 33.5k）。
- 在这个会话上续跑「只写进度」两次（收尾轮耗时主要取决于上下文大小、推理档与服务端，与上一轮是否被中止无关；这是替代做法，不完全等同于中止后的收尾）：
  - V2r：**185.1 秒**。会话文件时间戳：提问 `11:57:32`，答复 `12:00:29`，中间约 178 秒没有任何事件；输出 119 token、推理 0 token；本机 hook（SessionStart、UserPromptSubmit）在开头 3 秒内已结束。慢在模型服务端响应，不在本机。
  - V2r2（约 2 分钟后重测同一会话）：**13.5 秒**，输出同样 119 token。
- 结论：收尾轮通常十几秒，但会出现数分钟级的服务端长尾。做法 (a) 不能假设收尾轮一定在几十秒内返回，收尾轮自己也必须有硬期限，超时时要有不依赖模型的兜底（例如只报「已中止、会话 ID、可续跑」）。
- 另见：V2 答复把第 01 步标为「输出被截断，未能确定口令」——Codex 会截断大的工具输出，大文件读取不保证进上下文。

### V3 high 推理档下的时间预算收尾 —— 成立，余量仍小

同 E2b 的提示词（60 秒预算、≥45 秒不再开新步、90 秒兜底 SIGKILL），`high` 推理档：56.8 秒自己收尾，退出 0；完成 1–4 步，口令全对；没有执行第 5 步。余量 3.2 秒，与推理档 `none` 时（1.1–3.1 秒）同一量级。

### 补测顺带发现：写模式运行会改全局配置

`~/.codex/config.toml` 在补测后 sha256 变为 `7af49cdc…bed2`。修改时间 `19:54:10`，正是 V1 写模式运行启动时；内容是 Codex 自己追加的：

```toml
[projects."/Users/vilin/delegate-s35-probe2-20261026195358"]
trust_level = "trusted"
```

首轮 8 次只读运行都没有追加。也就是说，delegate 的 `--write` 首次在某个仓库运行时，Codex 会把该仓库永久记为「受信任」并写进用户全局配置。这是现有行为（与 S35 无关），是否在意交给负责人判断。经用户同意（原话「删掉临时仓库 ~/delegate-s35-probe2-20261026195358，也删掉 config.toml 里那条 trust 记录。」），已只删除这两行，sha256 恢复为测前的 `c84d6a4b…3c8b`；补测临时仓库也已删除。

## 未验证

- 真实 540 秒期限：本测试用 45/60 秒等比缩小。
- 收尾轮的长尾分布：只有 4 个样本（10.7、12.6、13.5、185.1 秒），长尾出现的频率不知道。
- 中止状态下的大上下文收尾：V2 没形成中止，用已完成的会话替代测量。
- 写模式下写到一半的文件、不提示「先看文件」时会不会重复写入。
- 其他模型：只测了 `gpt-6.1-sol`（推理档 `none` 与 `high`）。
- SIGINT 中止、单条命令跑数分钟时的行为没测（后者从机制上可知做法 (b) 拦不住）。
- 每项只跑了 1–2 次，稳定性是小样本结论。
